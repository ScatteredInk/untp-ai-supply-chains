# Proposed UNTP extension: AI compute and models (v0.1)

**Status: proposal by Open Data Services for discussion.** No part of this has been reviewed by UN/CEFACT or by any candidate owner. The namespace `https://example.org/untp-ai/0.1/` is a placeholder and does not resolve.

The extension adds vocabulary and rules on top of UNTP 0.7.0. It does not change core properties, and credentials that use it still pass the core schemas (see `validation-report.md`).

## Files

| File | What it is |
|---|---|
| `untp-ai-context.jsonld` | JSON-LD context. It is generated by `build.py` from the `aic:` terms actually used. Each term has a property-scoped context, so nested keys expand into the `aic:` namespace, and `value` and `unit` reuse UNTP's Measure terms. |
| `untp-ai-schema.json` | JSON Schema rules for each `aic:` property, plus the unit rule. |

## How it attaches to UNTP

- **Context.** A credential adds `https://example.org/untp-ai/0.1/context.jsonld` as the third `@context` entry, after VC v2 and UNTP 0.7.0.
- **Prefix.** Extension properties are always prefixed `aic:`. Unprefixed keys on a Facility or MakeEvent would expand silently into UNTP's type-scoped `@vocab` (for example `untp/Facility#installedEquipment`).
- **Where extension properties can sit.** They go only on objects the core schema leaves open (`additionalProperties: true`): the credential subject, `characteristics`, `Claim`. Closed objects (`Measure`, `Classification`, `Link`, `PartyRole`, `EventProduct`) cannot carry them.
- **Vocabulary through core fields.** Code lists are carried in core `Classification` fields (`productCategory`, `activityType`, `equipmentType`) by pointing `schemeId` at an extension scheme. This is the route UNTP intends for industry vocabularies (DTE requirement TEV-09).

## Vocabulary

### Product classes (`schemeId` `https://example.org/untp-ai/0.1/productClass`)

| Code | Name | Used for |
|---|---|---|
| `gpu-accelerator` | GPU accelerator | H100 passport; installed equipment |
| `gpu-server` | GPU server node | Jupiter servers |
| `cloud-vm` | Cloud virtual machine (GPU) | Augusta A3 Mega VMs |
| `storage-cluster` | Storage cluster | Jupiter WEKA cluster |
| `training-dataset` | Training dataset | olmo-mix-1124, dolmino-mix-1124 |
| `foundation-model` | Pretrained foundation model (base) | OLMo 2 7B |

These sit alongside the nearest UN CPC v2.1 code: 45290 for the GPU and 84399 for datasets and models. CPC has no class that fits either.

### Activity types (`schemeId` `https://example.org/untp-ai/0.1/activityType`)

| Code | Meaning |
|---|---|
| `training` | Producing or updating model weights by optimisation over a dataset (used in both DTEs) |
| `pretraining`, `mid-training`, `post-training` | Stages of training (used in `aic:trainingData.stage`) |
| `model-averaging` | Combining checkpoints, for example OLMo 2 7B's average of three 50B-token runs (proposed, not yet used) |

GS1 CBV Business Step has no training step.

### Units

UN/CEFACT Rec 20 has no codes for these. Extension units are **full IRIs**, because UNTP types `unit` as `@vocab` against the Rec 20 namespace, so a bare `FLOP` would expand to a non-existent Rec 20 IRI.

| IRI | Meaning |
|---|---|
| `https://example.org/untp-ai/0.1/unit#FLOP` | floating-point operations |
| `https://example.org/untp-ai/0.1/unit#TOKEN` | tokens (tokeniser-dependent; the tokeniser is identified by the model) |
| `https://example.org/untp-ai/0.1/unit#GPU-HOUR` | GPU-hours |
| `https://example.org/untp-ai/0.1/unit#PARAMETER` | model parameters |

Everything else uses Rec 20: MWH, KGM, TNE, MTQ, LTR, WTT, C62, AD (byte), E34 (GB), E35 (TB), E36 (PB), MMK (mm²).

### Metrics (`https://example.org/untp-ai/0.1/metric/…`)

| Slug | Meaning | Why |
|---|---|---|
| `pue` | Power usage effectiveness (ratio, C62) | No UNTP performance metric |
| `wue-offsite` | Off-site water usage effectiveness (litres per kWh) | No UNTP performance metric |

Energy, emissions, grid intensity and water use the existing UNTP metrics: `total-energy-consumption`, `total-ghg-emissions`, `ghg-emissions-intensity` and `water-consumption`.

### Identifier rule for models and datasets

1. `modelNumber`: the repository ID, for example `allenai/OLMo-2-1124-7B`.
2. `batchNumber`: the commit hash that fixes the exact bytes.
3. `aic:artefactFiles`: the SHA-256 of each distributed file.
4. Product `id`: the hub URL at the commit, `https://huggingface.co/{repo}/tree/{commit}`.
5. `idGranularity`: `batch`.

A registered persistent scheme would be better than a hub URL. SWHID is a candidate; it is believed to be standardised as ISO/IEC 18670, which has not been checked.

## Properties

| Property | On | Purpose |
|---|---|---|
| `aic:installedEquipment` | Facility | Capital equipment used at the facility but not consumed (contrast `materialUsage`) |
| `aic:computeTenant` | Facility | The party whose workloads run there (no tenant role in PartyRole) |
| `aic:equipmentUsed` | MakeEvent | Equipment used by the event, with GPU-hours |
| `aic:trainingShare` | MakeEvent | Share of the training done in this event |
| `aic:producedAtFacilities` | Product | Every facility that produced the product (`producedAtFacility` holds only one) |
| `aic:tokenCount`, `aic:byteSize`, `aic:documentCount`, `aic:composition`, `aic:sampleComposition`, `aic:licence` | Dataset `characteristics` | Size, composition and licence |
| `aic:architecture`, `aic:parameterCount`, `aic:layerCount`, `aic:hiddenSize`, `aic:contextLength`, `aic:vocabularySize`, `aic:tensorDtype`, `aic:licence`, `aic:artefactFiles`, `aic:totalArtefactSize`, `aic:trainingCompute`, `aic:trainingTokens`, `aic:trainingData` | Model `characteristics` | Model description, identifier rule and training inputs |
| `aic:die`, `aic:processNode`, `aic:transistorCount`, `aic:dieArea`, `aic:memoryCapacity`, `aic:memoryType`, `aic:thermalDesignPower`, `aic:formFactor`, `aic:components`, `aic:chipExplorerInputs` | GPU `characteristics` | Chip description, bill of materials, ETO Chip Explorer input IDs |

## Not covered

- **Ownership and control.** Out of UNTP scope; link parties to BODS statements instead.
- **Hosting and redistribution after release.** Out of scope; see the gap register.
